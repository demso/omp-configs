Гайд 0001 · Oh My Pi

Bigpowers без карго-культа

Bigpowers — это операционная система работы AI-разработчика: набор узких skills, проектных артефактов и quality gates. Его цель — не заставить агента написать больше кода, а сделать результат воспроизводимым, проверяемым и пригодным для передачи следующему агенту.

1. Что это и зачем

Обычная работа с coding agent часто выглядит так: пользователь дал длинное сообщение, агент нашёл несколько файлов, внёс правку и сказал «готово». Такой процесс оптимизирует скорость ответа, но не качество. Он теряет контекст, не фиксирует границы задачи и смешивает план, реализацию и проверку.

Bigpowers разделяет эти виды работы. Каждый skill отвечает за одну функцию, а состояние переносится не в память чата, а в файлы проекта. Поэтому качество становится свойством процесса, а не удачей конкретного запуска модели.

Главная формула: намерение → ограниченный scope → вертикальный план → изолированная реализация → проверка поведения → независимый review → интеграция.

Не является

Автономным менеджером, который всегда должен пройти все 80 skills; заменой инженерного мышления; гарантией правильности без запуска проверок.

Является

Каталогом процедур с входами, выходами и handoff. Вы выбираете процедуру по состоянию работы, а не по названию, которое лучше запомнилось.

3. Как читать проект в Oh My Pi

Первый вопрос после входа в проект: какое состояние уже зафиксировано? Не начинайте с редактирования файла и не выбирайте skill по памяти.

specs/state.yaml                  # текущий flow, epic, handoff
specs/product/SCOPE_LATEST.yaml   # границы инициативы
specs/release-plan.yaml            # порядок epics
specs/epics/eNN-slug/              # stories и tasks
specs/execution-status.yaml        # фактический статус выполнения
specs/verifications/               # доказательства проверки

Для этого существует survey-context. Он читает state, specs, conventions и VCS, затем сообщает фазу, blockers и следующий skill. В нормальном рабочем цикле это точка входа для существующего проекта.

Красный флаг: если state.yaml говорит одно, а код или VCS — другое, не «чините» state на глаз. Сначала разберитесь, какой источник устарел, иначе следующий агент продолжит неверный маршрут.

4. Planning spine: три разных действия

Самая важная часть bigpowers — не запомнить три названия, а не смешивать их смысл.

  1. scope-work — границы. Формулирует value, in-scope, out-of-scope, ограничения и success criteria. Здесь нельзя прятать архитектуру: «храним в PostgreSQL» — решение, а не scope.
  2. slice-tasks — вертикальные stories. Делит scope на самостоятельные пользовательские срезы. «Добавить все модели» — горизонтальный слой; «пользователь создаёт заказ и видит его» — вертикальный срез.
  3. plan-work — исполнимые задачи. Уточняет каждый story до шагов что сделать → verify: runnable command. Если критерий нельзя проверить командой или описанным UAT, история ещё не спланирована.

Если scope допускает две разные трактовки, сначала нужен пользовательский выбор. Нельзя компенсировать неоднозначность более подробным кодовым планом.

5. Правильные сценарии использования

Сценарий A — новая существенная фича

survey-context→elaborate-spec→scope-work→slice-tasks→plan-work→build-epic
  1. Проверьте, есть ли уже vision, scope и release plan.
  2. Уточните пользовательскую ценность и исключения.
  3. Нарежьте первый tracer-bullet: минимальный путь через все слои.
  4. Для каждого task запишите риск и запускаемую проверку.
  5. Реализуйте на feature branch, затем пройдите verify, audit и release handoff.

Сценарий B — точечный bug fix

survey-context→investigate-bug→diagnose-root→develop-tdd→validate-fix

Не начинайте с «попробую заменить эту строку». Сначала нужна воспроизводимость и гипотеза о причине. validate-fix должен подтвердить исходный failure, полный набор механических gates и отсутствие рецидива. Если дефект затрагивает несколько модулей, добавьте impact analysis.

Сценарий C — уже написанный код

verify-work→audit-code→request-review

Это не повод пересоздавать план с нуля. Проверьте обещанное поведение, запишите gaps, затем проведите self-audit и независимый review. Если UAT не проходит, возвращайтесь к реализации, а не снижайте критерий.

Сценарий D — низкорисковый change

Для простой локальной правки используйте короткий маршрут: survey-context → правка на изолированной ветке → профильная smoke/typecheck/lint проверка → commit-message. «Fast-track» уменьшает церемонию, но не отменяет проверку и не разрешает работать прямо на main.

6. Как bigpowers стабилизирует качество

1 · Контекст

State и specs уменьшают потерю решений между сессиями и агентами.

2 · Границы

Out-of-scope и delta-теги защищают от незаметного расширения задачи.

3 · Дробление

Vertical slices обнаруживают интеграционные ошибки раньше горизонтальных слоёв.

4 · Проверка

Runnable verify-команды превращают субъективное «готово» в наблюдаемое состояние.

5 · Независимость

Свежий reviewer снижает риск, что автор не заметил собственный дефект.

6 · Трассировка

Story, code, tests и evidence можно связать и найти тёмные требования.

Risk-scaled gates

РискРазумная глубинаНельзя потерять
P3Typecheck/lint или профильная проверка.Доказательство, что изменённый путь не сломан.
P2Smoke, typecheck, lint; без полной security/UAT церемонии.Реальный запуск изменённой поверхности.
P1Build, typecheck, lint, tests по проектным правилам, ручной UAT.Terminal verdict и сохранённое verification evidence.
P0Полный verify, security review, blind spots и NFR evidence.Явный go/no-go по безопасности, производительности, надёжности и эксплуатации.
Нельзя подменять gates текстом. Терминальный verdict — это один contiguous run команды с exit code. UAT — шаги пользователя и expected/actual. «Агент проверил» без команды, результата или evidence не является доказательством.

7. Неправильные сценарии

  • Вызвать orchestrate для каждой мелочи. Orchestrate предназначен для ясного multi-phase workflow. Для одного локального бага он создаёт шум.
  • Начать с plan-work без scope. Детализация не устраняет неясную цель; она только делает ошибочную трактовку дороже.
  • Сделать «сначала все модели, потом API, потом UI». Это задерживает интеграционный сигнал. Режьте вертикально.
  • Запустить несколько агентов на один и тот же файл без контракта. Это не параллелизм, а конфликт. Параллельте только независимые ownership-срезы.
  • Считать зелёный тест доказательством продукта. Тестовая команда — один gate; она не заменяет ручную проверку пользовательского обещания.
  • Исправить state так, чтобы gate стал зелёным. State описывает реальность; он не должен скрывать незавершённую работу.

8. Практический алгоритм для Oh My Pi

  1. Назовите тип работы: новая фича, bug, refactor, исследование или release.
  2. Запустите survey-context: прочитайте текущий handoff и blockers.
  3. Выберите глубину: полный lifecycle для существенного риска, fast-track для локального низкорискового change.
  4. Зафиксируйте обещание: кто получает какую наблюдаемую ценность.
  5. Зафиксируйте границы: in-scope, out-of-scope, success criteria.
  6. Нарежьте вертикально: каждая story должна давать демонстрируемую ценность.
  7. Сделайте verify runnable: не «проверить вручную», а конкретная команда или оформленный UAT-script.
  8. Изолируйте код: feature branch/worktree; не работайте прямо на защищённой ветке.
  9. Проверяйте обещание, а не только diff: smoke → механические gates → UAT → gaps loop.
  10. Оставьте handoff: state, status и evidence должны позволить продолжить работу без устного контекста.

10. Упражнение на реальном Oh My Pi

Возьмите следующую задачу и ответьте письменно до запуска агента:

  1. Какой тип задачи и почему?
  2. Какой риск P0–P3 и что это меняет в gates?
  3. Что является user-observable success criterion?
  4. Какой первый skill и какой следующий handoff?
  5. Какой минимальный vertical slice даст ранний интеграционный сигнал?
  6. Какая команда или UAT-шаг докажет каждый task?

Если на любой вопрос нет точного ответа, задача ещё находится в discovery/design, а не в build.
